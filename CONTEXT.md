## What it is

School workshop project (deliverable `Workshop2026-M2-G<n>-Code.zip`, no `.env` inside). Fictional payment
platform built to demo **autonomous recovery**: an attacker PC breaks a service, the incident is detected, a
remediation engine restarts the service on its own, and recovery is **proven** by a new successful
transaction and a consistent ledger. Team split: backend (this repo), React front, Grafana/Prometheus/Loki, ML
detector, cyber (attack + WAF/SIEM), governance (PCA/PRA). Code comments and user messages are in French.

Lab network: host PC `192.168.137.1` runs Docker Desktop (WSL2); attacker on `192.168.137.0/24`.
Only gateway `:8080` is exposed to the LAN; Grafana is `127.0.0.1:3000` only.

## Layout

```
gateway/nginx.conf           routes /api/<svc> -> <svc>:8000, login rate limit 10r/m burst 5, JSON access log
db/init/01-roles.sh          svc_* roles + schemas (runs once, on pgdata volume creation)
db/init/02-schema.sql        tables + minimal GRANTs (changes need `docker compose down -v`)
libs/common/resilience_common/
  app.py       create_app(service, db_schema=, startup=, shutdown=): /health /ready /metrics, request-id, JSON logs
  security.py  bcrypt, HS256 JWT, require_roles(...), require_service(...), service_token(name) (60 s)
  events.py    audit(...), notify(...): fire-and-forget, 2 s timeout, never fails the caller
  db.py        asyncpg pool, search_path = service schema, 30 retries at startup
  logs.py      log_event(logger, "snake_case_event", **fields)
services/<name>/app/main.py  one file per service; one shared services/Dockerfile (--build-arg SERVICE=)
scripts/     gen_env.py (secrets), smoke.py (end-to-end via gateway), export_openapi.py
infra/       prometheus (5 s scrape), promtail (labels: service, level), grafana datasources
```

## Services

| Service | DB schema | Docker restart | Purpose |
|---|---|---|---|
| auth | auth | `no` | register, login, JWT (15 min, no refresh); seeds `admin` from `ADMIN_PASSWORD` |
| accounts | accounts | `no` | accounts + immutable ledger; `/internal/transfer` (payments only), `/internal/integrity` |
| payments | payments | `no` | `Idempotency-Key` required; pending -> completed/failed; reconcile loop every 15 s |
| notifications | notifications | `no` | simulated email, stores notifications |
| audit | audit | unless-stopped | append-only, SHA-256 hash chain, `/api/audit/verify` |
| remediation | none | unless-stopped | alert -> restart via Docker proxy -> prove recovery |
| canary | none | unless-stopped | real 0.01 EUR payment via gateway every 5 s |

`restart: "no"` on the 4 business services is deliberate: Docker must not hide the outage, remediation brings them back.

## Mechanics worth remembering

- **Auth model**: user JWTs and service JWTs share one `JWT_SECRET` (HS256). Service tokens have
  `role=service`, `sub=<caller>`. `require_service("payments")` checks `sub`. Anyone with the secret can mint
  any token (known, documented limit).
- **Payment path**: payments inserts `pending` row (unique on `created_by, idempotency_key`) -> POST
  accounts `/internal/transfer` with `tx_id = payment.id` -> accounts locks both rows `ORDER BY id FOR UPDATE`,
  checks owner/currency/balance, writes debit+credit in one transaction. Ledger `UNIQUE(tx_id, account_id,
  direction)` makes replays return `already_applied`.
- **Ledger down**: transient errors (conn error, 5xx, 401, 408, 429) leave payment `pending` and return 503
  `{"detail": {"error": "ledger_unavailable", ...}}` with `Retry-After: 5`. Reconciler replays pending > 10 s old.
- **Business refusal**: 201 with `status: "failed"` + `failure_reason`. Only amount cap and same-account are 422.
- **Remediation flow**: `detected -> remediating -> verifying -> resolved`, or `failed / escalated /
  suppressed`. `type=anomaly` on a healthy service = `escalated`, no restart (preserve evidence). Whitelist of
  4 containers (`rsl-auth|accounts|payments|notifications`). One active incident per service. Circuit
  breaker: 3 per service per 10 min. Proof = `/ready` (90 s max) + up to 5 canary probes + ledger integrity.
  Incident history is in memory only (audit + Loki keep the durable trace).
- **Canary alerting**: 3 consecutive failed probes -> alert to remediation for each service whose `/ready`
  is down, otherwise the service mapped from the failed phase (`login->auth`, `accounts`, `payment->payments`).
  30 s cooldown per service. `CANARY_ALERTS_ENABLED=false` turns this off (to test the detector alone).
- **Detector integration**: be on `backend` network, POST `http://remediation:8000/internal/alerts` with
  `service_token("detector")`, body `{source, service, type, severity, score, details}`.
- **Prometheus label gotcha**: target label `service` collides with metric label `service`, so the metric's
  value lands in `exported_service` (e.g. `canary_service_ready{exported_service="payments"}`). Decide on
  `honor_labels: true` **before** building dashboards.

## Gaps found in the code (not in the README)

These affect the demo. Not fixed yet.

1. **auth outage is invisible to the canary for up to ~14.5 min.** `_ensure_session`
   (`services/canary/app/main.py:65`) reuses the cached token until 30 s before expiry, and payments validates
   JWTs locally. With auth down, the probe still succeeds, so `consecutive_failures` stays 0 and no alert goes
   out. `canary_service_ready{...auth}` does drop to 0. If the attack targets auth, only the detector (or
   token expiry) triggers remediation.
2. **notifications outage never triggers a canary alert.** `notify()` is best effort, so the probe stays
   `ok`. Alerts fire only on probe failure (`_record`, line 174). notifications only gets remediated if
   another service fails at the same time, or through the detector.
   Possible fix for 1 and 2: in `_record`, also count a probe as failed (or alert directly) when any service in
   `ready` is false.
3. **Login lockout is per username too**, so an attacker can lock out `admin` or `canary-bot` with 5 bad
   passwords a minute. Locking `canary-bot` makes the canary fail at token renewal and report `auth`, which
   leads remediation to restart auth. That restart wipes the in-memory counters, so it "fixes" the lockout.
   Interesting for the cyber scenario, but the result is misleading.
4. Payment idempotency replay check compares `from_account, to_account, amount` but not `currency`
   (`services/payments/app/main.py:175`).
5. audit is not watched by the canary at all (it relies on `unless-stopped`). A hung but running audit
   would go unnoticed except through `event_delivery_failed` logs.
6. `tecnativa/docker-socket-proxy:latest` is unpinned and allows restart/stop/kill on **any** container;
   the whitelist exists only in remediation code (already in README section 12).
7. `log_event(..., service=...)` overwrites the JSON `service` field of the emitting service (canary and
   remediation log lines claim `"service": "accounts"`). Loki labels come from Promtail, so queries still
   work, but `| json | service=` filters would mislead.
8. Front-specific: every request reaches the gateway from the Next.js server IP, so login rate limits
   (Nginx 10/min, auth 5 failures/min) are shared by all front users. Hit for real during testing.
9. Failed remediation attempts poison the circuit breaker: 3 failures in 10 min → `suppressed` until the
   window passes or remediation restarts.

## Conventions

- Log events and audit actions are `snake_case`, and each name keeps a stable meaning (LogQL and SIEM rules depend on them).
- Amounts are `Decimal` and serialized as strings. IDs are UUID v4. Timestamps are UTC ISO 8601.
- No DDL from services. No cross-schema foreign keys (references are logical).
- To add a service: `services/<name>/app/main.py` with `app = create_app(...)`, then add a compose block, a
  Prometheus target, and an entry in `export_openapi.py`. A new DB schema also needs `01-roles.sh`, `02-schema.sql`
  and `.env.example` changes.
